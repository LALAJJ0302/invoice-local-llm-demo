### 0.1 The evaluation harness now reports a number that is not true

This is the serious one and it should be fixed today.

`evaluation/run_eval.py` measures extraction accuracy with the heuristic fallbacks switched off, so
that we measure the model rather than our own patches. It does that by neutralising one method at
line 84:

```python
extractor._infer_vendor_fallback = lambda raw_text, file_name: None
```

The new commit adds a **second** fallback, `_infer_missing_fields_fallback`, and calls it
unconditionally inside `extract_invoice_data`. The harness does not know it exists, so it does not
switch it off.

The result is that the harness prints this:

```
=== Extraction accuracy: llama3.2 (heuristic fallbacks: disabled) ===
OVERALL              14/15       93.3%
```

**The fallbacks are not disabled.** Four of those five fields were filled by regular expressions,
not by the model. The label on the output asserts something false, and 93.3% is not a measurement
of what the line above it claims to measure.

I want to be careful about how this is said, because it is not an accusation. The regex code is
reasonable engineering and I will argue for keeping it in the pipeline. The problem is narrower and
worse: **it silently broke the instrument we use to measure ourselves.** Anyone who ran that command
this week would have copied 93.3% into a report in good faith.

**Fix:** `run_eval.py` should neutralise both fallbacks under the same flag. I can do it in ten
minutes, and `evaluation/evaluation-method.md` needs a line saying the flag covers every fallback,
not one named method, so the next one added does not repeat this.

### 0.2 The prompt change is a genuine result, and it partly contradicts what we have been saying

The same commit rewrites the extraction prompt: it adds an instruction not to leave a field at its
default, and one worked example.

I measured the model on its own, with **both** fallbacks disabled, three times:

```
OVERALL  10/15  (66.7%)     run 1, run 2, run 3, identical
```

Our committed baseline is 3/15. **The prompt change alone took the model from 3/15 to 10/15**, and
it is stable across runs, so it is not decoder noise.

This matters for the report and I would rather we found it than a marker did. Our documentation
currently says, in more than one place, that these failures should not be blamed on the model or
addressed with prompt engineering. **That claim is now too strong and has to be softened.** The
controlled comparison is still valid, because it held the prompt fixed and changed only the schema,
so the schema is still shown to be a cause. But it is no longer honest to say the prompt is not
one.

The strongest accurate statement we can now make:

> Both the schema and the prompt contribute. Required fields take extraction to 15/15 on their own.
> A better prompt takes it to 10/15 on its own. The original 3/15 was the two worst versions of
> each, together.

That is a more interesting finding than the one we had, not a weaker one.

## C. D3, the extraction fix (10 min): the big one

**This item changed today.** We now have three different answers to the same problem sitting in
front of us, and two of them are already written.

| Approach | Result on its own | Where it lives | Status |
|---|---|---|---|
| Required fields on `ExtractedInvoice` | **15/15** | measured in `evaluation/schema_comparison.py` | measured, not shipped |
| Better prompt | **10/15** | `main.py`, pushed today | shipped |
| Regex fallback after the model | fills the gaps deterministically | `main.py`, pushed today | shipped |
| What we had | 3/15 | committed baseline | superseded |

JJ's review asked for the extraction fix to be a separate PR. That is still the right shape. But
the question is no longer "do we fix it" and has become "**which of these do we keep, and what do
we then claim?**"

My position, and I will argue for it but I am one of three:

**1. Keep the regex fallback.** For highly patterned fields like an invoice number, a regular
expression is not a workaround, it is the correct tool. Asking a 3B model to do it and hoping is
worse engineering. I would rather defend this in the report than pretend it is embarrassing.

**2. Still make the schema fields required.** The regex hides the root cause rather than removing
it. If the schema stays `Optional`, the model keeps emitting nothing and the regex quietly carries
the pipeline. That is fine right up until a document the regex does not match, at which point we
have no idea how bad the model actually is, because we stopped measuring it.

**3. This is the condition, and it is not optional: the fallbacks must stay measurable
separately.** See item 0.1. Whatever we keep, `run_eval.py` must be able to switch every fallback
off, so we can always answer "what does the model do by itself". The moment we cannot answer that,
the evaluation section of the report is worthless.

**4. Report all of it.** Before, after, and the fact that there were two independent causes rather
than one. Our strongest result is not a high accuracy number. It is that we found specific,
non-obvious causes in our own code, isolated them, and can show the working. If we ship a fix
quietly and report only the final figure, we throw away the best evidence we have that we
understood our own system.

One cost that still needs a group decision, unchanged from the last sync: required fields make the
model **invent values for 3 of the 9 fields that are genuinely absent** from the documents. With
`Optional` it invents zero. A sentinel value was measured as a mitigation and performs identically
to plain required fields, so it does not help. We are trading blank fields for confident wrong
ones, and someone other than me should agree to that trade.
