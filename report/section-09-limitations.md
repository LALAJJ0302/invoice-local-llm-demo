# 9. Limitations and Future Work

This section collects the boundaries of everything claimed above. They appear throughout the
report at the point where each result is stated, and they are gathered here so that a reader can
see them together rather than assemble them from six places.

The consolidation is deliberate and it is not neutral. Limits stated one at a time, each beside a
result it qualifies, read as reasonable caveats. The same limits read consecutively give a
different and more accurate impression of how far this work generalises, which is not far. That
impression is the correct one.

## 9.1 The sample bounds every number in this report

**Three synthetic documents, generated by the team.** Every accuracy figure rests on them. They
were produced with ReportLab and therefore have a clean text layer, consistent spacing, no logos,
no stamps, no multi-column layouts and no handwriting. They contain the layouts the team thought
of. SROIE, a standard benchmark for the same task, provides 347 real scanned receipts in its
test split alone and labels four fields where this project labels five.

**Three is too few to separate a real difference from chance**, and §7.12 showed exactly how
that bites. Changing one word in the prompt moved the result from 10/15 to 15/15, which reads as
a decisive 33 percentage points. What actually happened is that **one document went from 0/5 to
5/5 and the other two did not move.** The entire effect is a single observation. It reproduced
across nine runs, so it is not noise in the measurement, but reproducibility is not
generalisability: nothing in this evaluation can say whether that prompt defect would have
affected the fourth document, or the fortieth.

This is the sharpest available illustration of why the sample size is the limiting factor rather
than a caveat. With three documents, one document is a third of the evidence, and a result driven
entirely by one document is indistinguishable in shape from a result that holds everywhere.

**One model carries every accuracy claim.** `llama3.2` produced all of the field-level results.
The six-model comparison establishes that the other models accept constrained decoding, not that
they extract equally well.

**The gate's heuristics were fitted to these same three documents.** The rule that an amount must
appear within two lines of a total label holds because the generator puts them there. An invoice
placing the amount in a table cell would fail it. The rule was not derived from a study of
invoice layouts; it was derived from the three files available.

## 9.2 What was never measured at all

**The email half has no ground truth, and this is the largest unmet requirement in the project.**
Classification, summarisation and action extraction run, and their output is stored and
queryable, but there is no labelled set, so nothing in that half has an accuracy figure. The
report can say what a run produced and cannot say whether it was right.

The asymmetry matters more than the gap. Extraction is scored against independently transcribed
ground truth; the email half is not scored at all. Presenting the two halves side by side risks
implying the second is as well evidenced as the first. Every figure reported for the email half
is a count of what the pipeline did, never of what it got right.

**Building that labelled set is a larger job than it sounds.** A set of invoice-related emails is
not sufficient: all 18 messages in the current mailbox are correctly classified `Invoice`, so a
classifier that ignored its input entirely would score perfectly. The set has to contain messages
that genuinely are not invoices, which means writing them, which means first deciding what a
correct summary is before anything can be marked wrong.

**No scanned document has ever passed through the pipeline.** Extraction requires a PDF text
layer and there is no OCR stage, so the most common real-world invoice format is untested rather
than merely unsupported.

**The gate has never been tested against fraud, duplication, or an unknown vendor.** Every check
it performs is internal to the document, so a well-formatted document that should not be paid
scores exactly as well as one that should. §9.4 returns to this.

## 9.3 Threats to validity

**Construct validity.** `validation_score` measures field completeness and agreement with the
source text. It is not a confidence score and does not estimate the probability that an
extraction is correct. §7.11 sets out what it does measure, and the column was renamed in the
database for this reason.

**Score comparability.** The gate's weighting changed on 28 August and again on 3 September 2026.
Scores are not comparable across those dates, and each figure in this report is marked with the
period it belongs to.

**Internal validity.** A discrepancy between two of the project's own figures, 6/15 against 3/15,
was traced to a difference in schema shape and resolved. It is retained in the report because
finding it required treating two disagreeing numbers as a defect rather than quietly choosing
one.

**External validity.** Three synthetic documents from one generator. Nothing in this report
supports a claim about performance on real invoices, and no such claim is made.

**Non-determinism.** Language models are not deterministic, so a small difference between two
figures is not necessarily a real one. Where a difference is reported as real, it was run
repeatedly and the runs are stated.

## 9.4 The limit that no improvement in extraction closes

The group agreed that a validation score of 1.00 should skip human approval. **That should not be
implemented in its current form, and it is the project's most important recommendation.**

The gate asks whether extracted values match the text on the page. It cannot ask whether the
invoice is a duplicate, whether the vendor is one the organisation buys from, or whether the
document is a well-formatted fraud. All three score 1.00 today. Reading accuracy is not payment
authority, and no amount of the former produces the latter.

The clearest demonstration is the statement of account in §7.5.1. Presented with a document
containing no total, every required-family schema returned `2000.00`, arrived at by adding an
opening balance of 1,200.00 to payments received of 800.00. The model is not fabricating a value
from nothing; it is performing arithmetic on the page, and the arithmetic is wrong in kind, since
a payment received should be subtracted. **A fabricated value can be caught by asking whether it
appears in the document. A computed value passes that test by construction**, and is
arithmetically consistent with the page, which is what makes it convincing.

Three things are prerequisites rather than improvements before any auto-approval ships: duplicate
detection on `(vendor, invoice_number)` rather than on a content hash, a vendor allow-list that
necessarily leaves the document, and an audit trail in which an automatic approval is
distinguishable from a human one.

## 9.5 Specified and measured, deliberately not shipped

Four changes exist as specifications with measured results and were not merged, because each
alters behaviour the whole group depends on and the group had not decided. Listing them as future
work rather than omissions is the accurate framing.

| Change | Evidence | Why it was held |
|---|---|---|
| Adopt the nullable-required schema | §7.5.1 | Matches the best accuracy of any schema tested and produces the fewest classified errors, but not for the reason originally argued: it does not end invented values |
| Verify the date and currency in the gate | Preview run | Both are checked for non-emptiness only, so a wrong date and an invented currency both pass today |
| Fix the subtotal defect in the same change | Not yet fired | The label matcher tests `total` as a substring and `total` occurs inside `subtotal`, so a pre-tax subtotal is accepted as a grand total. It will fire on the first real invoice carrying GST |
| Ship hybrid retrieval | Retrieval evaluation | Neither shipped strategy dominates; hybrid is the only one that is never worst on either query type |

## 9.6 A decision the report cannot make for the group

§7.12 removed the justification for a component that is currently shipped. The regex fallback and
the caption stripper exist to repair the model's output, and the report credits them with the
difference between 10/15 and 15/15. With the prompt label corrected, the model alone returns
15/15 and the run with every repair enabled returns 15/15 as well. **On this sample set the
repair code repairs nothing.**

Two readings are available and the evidence does not choose between them. The repair code may be
redundant, in which case it is 92 lines of regex carrying a maintenance cost for no benefit. Or
it may be insurance against documents this sample does not contain, in which case removing it
would be trading a measured present cost for an unmeasured future risk. §9.1 is the reason the
second cannot be dismissed: three documents cannot establish that a safeguard is unnecessary.

What the report can say is that the justification currently written for it is no longer the true
one, and that the group now has a decision it did not know it had.

## 9.7 Functional gaps for a later team

**OCR first.** No accuracy improvement matters to an organisation whose invoices arrive as
images.

**Real documents, with ground truth extended before they arrive.** Every heuristic here is fitted
to three generated files and the ground-truth file covers only those three. Adding real invoices
without extending it first would mean running experiments with no way to tell whether they
helped, which would undo the one methodological commitment this project has kept. The email half
is already in exactly that state, which is the clearest argument for the ordering.

**Thread identity from headers rather than subject lines.** Conversations are currently
reconstructed by matching subjects, and one of sixteen threads in the test mailbox is a known
subject collision. The correct key is `In-Reply-To` and `References`, which requires a change to
intake.

**Embedding-based retrieval, now justified where previously it was not.** A third strategy was
deliberately not built, on the reasoning that adding one before measuring the two that already
existed would produce a preference rather than a result. That measurement now exists.

**The outbox has one unimplemented consumer.** No Teams message is sent and no Jira task is
created; every row remains pending. This is a defined interface rather than an incomplete
feature, and it should be handed to a later team as such.
