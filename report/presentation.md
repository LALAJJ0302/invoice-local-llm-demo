## 1.1 ทำไม ground truth ต้องถอดด้วยมือ ไม่ดึงจากสคริปต์ที่สร้าง PDF

**คำตอบสั้น** เพราะจะกลายเป็นการเอาสคริปต์ไปสอบตัวเอง

**เหตุผล** `generate_mock_invoices.py` มี dict ที่เก็บข้อมูลใบแจ้งหนี้อยู่แล้ว เช่น
`"total_amount": 1500.00` ถ้าเอาเลขนั้นมาเป็นเฉลย เรากำลังเทียบสิ่งที่โมเดลอ่านได้ กับสิ่งที่สคริปต์**ตั้งใจจะเขียน**

แต่สิ่งที่เราต้องการวัดคือ โมเดลอ่าน**สิ่งที่อยู่บนหน้ากระดาษจริง**ได้ไหม ซึ่งอาจไม่ตรงกับที่สคริปต์ตั้งใจ
เช่นถ้า ReportLab วางตัวเลขทับกัน หรือ pypdf ดึงข้อความออกมาผิดลำดับ เฉลยที่มาจาก dict จะมองไม่เห็นปัญหานั้นเลย

**พูดอีกแบบ** ถ้าสคริปต์สร้างมีบั๊ก เฉลยจะมีบั๊กเดียวกัน แล้วเราจะได้คะแนนเต็มทั้งที่ระบบพัง

**หลักฐาน** `evaluation/ground_truth.json` เขียนกำกับไว้บรรทัดแรกเลย

```
"_comment": "Independently transcribed from the rendered PDFs, not imported from
generate_mock_invoices.py. Deriving ground truth from the generator would test the
generator against itself."
```

**ทำไมเรื่องนี้ได้คะแนน** เกณฑ์ข้อ Quality of project outcomes ดูว่าการประเมินน่าเชื่อถือไหม
กลุ่มส่วนใหญ่จะดึงเฉลยจากสคริปต์เพราะง่ายกว่า และมองไม่เห็นว่ามันเป็นการวัดที่ไม่มีความหมาย

## 1.2 3/15 มาจากไหน ทำไมเป็น 15

**คำตอบสั้น** 3 เอกสาร คูณ 5 field ต่อเอกสาร = 15 ช่องที่ต้องกรอก โมเดลกรอกถูก 3 ช่อง

```
                 ใบ1   ใบ2   ใบ3        รวม
vendor_name       ✓     ✓     ✓         3/3   100%
invoice_number    ✗     ✗     ✗         0/3     0%
date              ✗     ✗     ✗         0/3     0%
total_amount      ✗     ✗     ✗         0/3     0%
currency          ✗     ✗     ✗         0/3     0%
                                       -----
                                       3/15    20%
```

**5 field คือ** `invoice_number`, `vendor_name`, `date`, `total_amount`, `currency`
ไม่นับ `items` เพราะเป็น list ไม่ใช่ค่าเดี่ยว วัดแบบถูก/ผิดตรง ๆ ไม่ได้

**เกณฑ์การนับว่าถูก** ไม่ใช่ต้องเหมือนเป๊ะทุกตัวอักษร
- ข้อความ ตัดช่องว่างซ้ำและไม่สนตัวพิมพ์เล็กใหญ่
- วันที่ เทียบเฉพาะตัวเลข `2026-08-10` เท่ากับ `10/08/2026`
- ตัวเงิน ต่างกันได้ไม่เกิน 0.01

ผ่อนแบบนี้เพื่อไม่ให้เรื่องรูปแบบการเขียนถูกนับเป็นความผิดพลาดของการสกัด

## ระวังสับสน มีสามตัวเลข ไม่ใช่ตัวเดียว

| ตัวเลข | วัดอะไร | ค่า |
|---|---|---|
| **3/15 = 20%** | โมเดลสกัด field ถูกกี่ช่อง | 20% |
| **0/3 = 0%** | ผ่าน gate อัตโนมัติกี่ใบ (automation pass rate) | 0% |
| **3/3 = 100%** | ยอดเงินที่**เก็บในฐานข้อมูล**ถูกกี่ใบ | 100% |

**ห้ามพูดว่า "ระบบได้ 100%"** เพราะ 3/3 นั้นไม่ได้วัดโมเดล มันคือยอดที่โค้ดเราบวกจาก line items

**ห้ามพูดว่า "ระบบได้ 0%"** เพราะท่อทำงานครบทุกขั้น

## 1.3 ทำไม vendor_name ได้ 3/3 แต่อีกสี่ตัวได้ 0/3 ทั้งที่ตั้งค่าเหมือนกันหมด

**คำตอบสั้น** เพราะ schema **อนุญาต**ให้ข้าม ไม่ได้**บังคับ**ให้ข้าม โมเดลเลือกตอบบางช่อง ไม่ตอบบางช่อง

ทั้งห้า field เขียนเหมือนกันเป๊ะ

```python
invoice_number: Optional[str]   = Field(default=None, ...)
vendor_name:    Optional[str]   = Field(default=None, ...)   <- โครงสร้างเดียวกัน
date:           Optional[str]   = Field(default=None, ...)
total_amount:   Optional[float] = Field(default=0.0, ...)
currency:       Optional[str]   = Field(default="Unknown", ...)
```

ไม่มีตัวไหนตั้งค่าต่างจากตัวอื่นเลย **แปลว่าการตั้งค่าผิดไม่ได้อยู่ที่ field ใด field หนึ่ง มันอยู่ที่ทั้งคลาส**

**เปรียบเทียบ** เหมือนแบบฟอร์มที่ไม่มีดอกจันสีแดงสักช่อง กรอกช่องเดียวแล้วกดส่งก็ผ่าน
ไม่ได้แปลว่าทุกคนจะกรอกช่องเดียว แต่แปลว่าใครจะกรอกช่องเดียวก็ได้

**ทำไมโมเดลเลือกตอบ vendor** ข้อนี้ต้องพูดให้ตรง **นี่คือการอนุมาน ไม่ใช่สิ่งที่วัดมา**
ชื่อผู้ขายอยู่บรรทัดบนสุดของเอกสาร เป็นข้อมูลที่เด่นที่สุด น่าจะเป็นเหตุผล แต่เราไม่ได้ทดลองยืนยัน

**สิ่งที่วัดมาจริง** พอเปลี่ยนเป็น required ปิดทางเลือกที่จะไม่ตอบ โมเดลตัวเดิมตอบครบและถูกทั้ง 15 ช่อง
แปลว่าโมเดล**อ่านออก**ตลอด แค่ไม่ได้ถูกบังคับให้ตอบ

**ถ้าโดนถามว่ารู้ได้ไงว่าโมเดลอ่านออก** ตอบว่า vendor_name ได้ 3/3 ตั้งแต่แรกโดยไม่ต้องแก้อะไร
ถ้าโมเดลอ่านเอกสารพวกนี้ไม่ออกจริง field นี้ก็ควรพังด้วย

# ส่วนที่ 2 เรื่องสาเหตุ

## 2.1 Optional กับ default ทำให้เกิดอะไรใน JSON Schema ที่ส่งให้ Ollama

**ลำดับเหตุการณ์ 5 ขั้น** อันนี้คือแกนของทั้งรายงาน ต้องเล่าได้คล่อง

**ขั้น 1** เราเขียนคลาส Pydantic ที่ทุก field เป็น `Optional` และมี `default`

**ขั้น 2** เราแปลงคลาสเป็น JSON Schema แล้วส่งให้ Ollama ผ่าน `format=`

```python
format=ExtractedInvoice.model_json_schema()
```

`format=` ไม่ใช่การขอร้องใน prompt แต่เป็นการ**บังคับที่ระดับการสร้างข้อความ** ตัว decoder
จะไม่ยอมสร้าง token ที่ทำให้ JSON ผิดรูป เรียกว่า constrained decoding

**ขั้น 3** แต่ schema ที่ส่งไปหน้าตาแบบนี้

```json
{
  "properties": {
    "invoice_number": { "anyOf": [{"type":"string"}, {"type":"null"}], "default": null },
    "total_amount":   { "anyOf": [{"type":"number"}, {"type":"null"}], "default": 0.0 },
    ...
  },
  "required": << ไม่มี key นี้เลย >>
}
```

ใน JSON Schema คำว่า `required` คือรายชื่อ field ที่**ต้องมี** Pydantic ไม่ใส่ key นี้มาเลย
เพราะทุก field มี `default` อยู่แล้ว ในสายตา Pydantic มันจึง "ไม่จำเป็น"

**ขั้น 4** โมเดลจึงข้ามได้อย่างถูกกฎ กฎบอกว่า "ถ้าจะตอบ ต้องตอบให้ตรงรูป" แต่**ไม่ได้บอกว่าต้องตอบ**
โมเดลตอบ `{}` ว่างเปล่าก็ยังผ่าน

**ขั้น 5** Pydantic เห็นว่า field หายไป เลยเติม default ให้

```
โมเดลไม่ตอบ invoice_number  ->  เติม None
โมเดลไม่ตอบ total_amount    ->  เติม 0.0
โมเดลไม่ตอบ currency        ->  เติม "Unknown"
```

**ขั้นที่ 5 คือส่วนที่ทำให้หาสาเหตุยาก** เราไม่เห็นว่าโมเดลข้าม เราเห็นแค่ค่าที่ดูเหมือนคำตอบ
ซึ่งจริง ๆ เป็นค่าที่เราเขียนใส่ไว้เอง

**หลักฐาน** รัน `./.venv/bin/python -c "from main import ExtractedInvoice;
print(ExtractedInvoice.model_json_schema().get('required','ไม่มี'))"` แล้วดูว่าไม่มี key นั้นจริง

## 2.2 ทำไมถึงบอกว่าไม่ใช่ความผิดโมเดล ใช้หลักฐานอะไร

**หลักฐานสามชิ้น** เรียงจากอ่อนไปแข็ง

**ชิ้นที่ 1 รูปแบบของความผิดพลาด**

```
invoice_number  = None        <- ตรงกับ default ของเราเป๊ะ
date            = None        <- ตรงกับ default ของเราเป๊ะ
total_amount    = 0.0         <- ตรงกับ default ของเราเป๊ะ
currency        = "Unknown"   <- ตรงกับ default ของเราเป๊ะ
```

ถ้าโมเดลอ่านไม่ออกจริง มันควรตอบ**มั่ว** เช่นเดา currency เป็น EUR หรือหยิบเลข 240.00 มาเป็นยอดรวม
แต่ที่เห็นคือมันตอบค่าที่เราตั้งไว้เอง**เป๊ะทุกครั้งทุกใบ** นั่นคือลายเซ็นของ "ไม่ตอบ" ไม่ใช่ "ตอบผิด"

**ชิ้นที่ 2 เอกสารเขียนชัดมาก**

```
บรรทัดในเอกสาร: "Invoice Number: INV-2026-001"
โมเดลตอบ:       None
```

ไม่มีอะไรกำกวมในบรรทัดนั้น มีคำว่า Invoice Number นำหน้าให้ด้วย และ prompt เราก็สั่งให้หา `Invoice #` อยู่แล้ว
**ข้อนี้ปิดข้ออ้างที่ว่า "โมเดลอ่านเอกสารรก ๆ ไม่เก่ง" ไปเลย** เพราะไม่มีอะไรรกในบรรทัดนั้น

**ชิ้นที่ 3 แข็งที่สุด เปลี่ยนตัวแปรเดียวแล้ววัด**

```
Optional  ->   3/15  (20%)
required  ->  15/15  (100%)
```

โมเดลตัวเดิม prompt เดิมทุกตัวอักษร เอกสารเดิม temperature 0 เท่ากัน
**ถ้าโมเดลเป็นสาเหตุ การเปลี่ยน schema ไม่ควรทำอะไรเลย** แต่มันเปลี่ยนจาก 20% เป็น 100%

## 2.3 "controlled comparison" คุมอะไรไว้บ้าง และเปลี่ยนอะไร

**หลักการ** ถ้าอยากรู้ว่า A เป็นสาเหตุของ B ต้องเปลี่ยนแค่ A แล้วดูว่า B เปลี่ยนไหม
ถ้าเปลี่ยนหลายอย่างพร้อมกันแล้วผลดีขึ้น จะบอกไม่ได้ว่าอะไรทำให้ดีขึ้น

**คุมไว้** (ต้องเหมือนกันเป๊ะทั้งสองรอบ)

```
โมเดล          llama3.2 ตัวเดียวกัน
prompt         คัดลอกมาจาก main.py ทุกตัวอักษร รวม 6 ข้อของ JJ
เอกสาร         ไฟล์ PDF สามใบเดิม
temperature    0.0  ทำให้ผลลัพธ์เหมือนเดิมทุกครั้งที่รัน
InvoiceItem    นิยาม field ย่อยเหมือนกัน
```

**เปลี่ยน** (ตัวแปรเดียว)

```
field ทั้งห้าเป็น Optional พร้อม default   หรือ   เป็น required ไม่มี default
```

**ผลของการเปลี่ยน** `required` list ที่ส่งให้ Ollama เปลี่ยนจาก **ไม่มี** เป็น
`['invoice_number','vendor_name','date','total_amount','currency']`

**ทำไม temperature 0 สำคัญ** ถ้าใช้ค่าอื่น โมเดลจะสุ่มคำตอบต่างกันทุกรอบ พอผลต่างกันจะแยกไม่ออกว่า
มาจาก schema หรือมาจากความสุ่ม ตั้งเป็น 0 ทำให้ผลลัพธ์เดิมทุกครั้ง ความต่างที่เหลือจึงมาจากตัวแปรที่เราเปลี่ยนเท่านั้น

**สิ่งที่การทดลองนี้พิสูจน์ และไม่ได้พิสูจน์** พิสูจน์ว่า **schema เป็นสาเหตุ**
ไม่ได้พิสูจน์ว่า **ระบบแม่น 100%** สองอย่างนี้คนละเรื่อง ดูส่วนที่ 4

# ส่วนที่ 3 เรื่องต้นทุนของทางแก้

## 3.1 required แก้ปัญหา หรือย้ายปัญหา

**คำตอบสั้น ย้าย และเราวัดปริมาณที่ย้ายมาแล้ว**

```
ก่อนแก้   โมเดลเงียบ      ->  ได้ None       ->  รู้ว่าไม่มีข้อมูล
หลังแก้   โมเดลต้องตอบ    ->  ได้ 'Table 4'  ->  ดูเหมือนมีข้อมูล แต่ผิด
```

พอเป็น required โมเดลคืน None ไม่ได้อีก เพราะ schema ระบุ `"type": "string"` ซึ่ง null ไม่ใช่ string
มันจึง**ต้องตอบอะไรสักอย่าง** และเมื่อถูกบังคับ มันก็แต่ง

**วัดมาแล้ว** ทดสอบกับ 5 เอกสาร มี 9 field ที่ไม่มีข้อมูลจริง

```
variant    | สกัด field ที่มีจริงถูก | ยอมรับว่าไม่มี
optional   |        1/13           |     9/9
required   |       12/13           |     6/9
```

**อ่านตารางนี้ให้ระวัง** `optional` ได้ 9/9 ในคอลัมน์ขวาซึ่งดูดีที่สุด **แต่ไม่ใช่ความดี**
มันได้เพราะไม่ตอบอะไรเลยตั้งแต่แรก ไม่ใช่การยอมรับ แต่เป็นความเงียบ ดูคอลัมน์ซ้ายคู่กัน 1/13

**สรุปที่ต้องพูดให้ครบ** required ยังคุ้มชัดเจน แต่แลกมาด้วยการแต่งข้อมูลราว 33% ของ field ที่ไม่มีจริง
ทางแก้ต้องอยู่ปลายทาง คือ validation gate ไม่ใช่ที่ schema

รันเอง `./.venv/bin/python evaluation/sentinel_comparison.py`

## 3.2 Table 4 กับ 2000.0 ต่างกันยังไงในแง่ความอันตราย

**สองเคสนี้เป็นคนละระดับ และเคสที่สองน่ากลัวกว่ามาก**

**เคส Table 4** ใบเสร็จร้านกาแฟ ไม่มีเลขที่ใบแจ้งหนี้ โมเดลไปหยิบ `Table 4` (เลขโต๊ะ) มาแทน

```
ประเภท    หยิบข้อความผิดที่มาใช้
ที่มา      มีอยู่ในเอกสารจริง แค่คนละความหมาย
จับได้ไหม  ยาก เพราะการเช็คว่า "ข้อความนี้มีในเอกสารไหม" จะผ่าน
```

**เคส 2000.0** ใบแจ้งยอดบัญชี เขียนว่า `Opening balance 1,200.00` และ `Payments received 800.00`
และระบุชัดว่า "for information only" ไม่มียอดที่ต้องจ่าย โมเดลตอบยอดรวม `2000.0`

```
1,200.00 + 800.00 = 2,000.00
```

**โมเดลบวกเอง** มันไม่ได้หยิบเลขผิด **มันคำนวณเลขใหม่ขึ้นมา**

```
ประเภท    สร้างข้อมูลใหม่ที่ไม่มีในเอกสาร
ที่มา      ไม่มีเลข 2000 อยู่ในเอกสารเลยสักที่
จับได้ไหม  การเช็คตำแหน่งจับไม่ได้ แต่เลขคณิตจับได้
```

**ทำไมเคสที่สองอันตรายกว่า**

หนึ่ง มัน**ดูสมเหตุสมผล** ใครอ่านผ่าน ๆ จะไม่สงสัยว่า 2,000 ผิด ต่างจาก `Table 4` ที่ดูแปลกทันที

สอง มันแสดงว่าโมเดล**ไม่ได้แค่คัดลอก มันสร้าง** ซึ่งเป็นความสามารถที่เราไม่ได้ขอ
และไม่มีทางรู้ว่ามันจะสร้างอะไรอีกในเอกสารที่เราไม่ได้ทดสอบ

สาม มันอยู่ในช่อง **ยอดเงิน** ซึ่งเป็นช่องที่ตัดสินว่าจะจ่ายเท่าไหร่

**นี่คือเหตุผลที่ต้องมี `reconciliation`** เพราะเทียบยอดรวมกับผลบวก line items เป็นเลขคณิต
ไม่ขึ้นกับว่าเอกสารวางยังไง จับเคสนี้ได้ตรง ๆ

## 3.3 ทำไม sentinel ถึงใช้ไม่ได้ และตอนแรกทำไมถึงคิดว่าใช้ได้

**sentinel คืออะไร** ค่าพิเศษที่จองไว้ให้แปลว่า "ไม่มี" เช่นบอกโมเดลว่า
"ถ้าหาเลขที่ใบแจ้งหนี้ไม่เจอ ให้ตอบ NOT_FOUND"

**ไม่ใช่ทางเลือกแทน required มันใช้คู่กัน**

```
Optional + default   ข้ามได้         ->  ข้ามเงียบ ๆ แล้ว default กลบ
Required เฉย ๆ       ข้ามไม่ได้      ->  ถูกบังคับ เลยแต่ง
Required + sentinel  ข้ามไม่ได้      ->  ตอบ NOT_FOUND ซึ่งเป็นคำตอบที่ซื่อสัตย์
```

จุดสำคัญคือ `None` กับ `NOT_FOUND` ต่างกัน อันแรกคือ**ความเงียบ** อันหลังคือ**คำให้การ**

**ตอนแรกทำไมคิดว่าใช้ได้** ทดสอบเอกสารเดียว ผลออกมาแบบนี้

```
required เฉย ๆ    invoice_number = 'Table 4'        <- แต่ง
sentinel          invoice_number = 'Not specified'  <- ยอมรับ
```

ดูเหมือนได้ผลชัดเจน จึงแนะนำว่าเป็นทางที่ดีที่สุด

**พอวัดจริงกลับไม่ใช่** ทดสอบ 5 เอกสาร 9 field ที่ขาด

```
required   |  12/13  |  6/9
sentinel   |  12/13  |  6/9    <- เหมือนกันเป๊ะ แต่งค่าเดียวกันทั้งสามตัว
```

**สาเหตุที่ผลแรกหลอก** เอกสารเดียว รันเดียว และ description ที่ใช้ในสองรอบไม่เหมือนกันเป๊ะ
ผลที่เห็นจึงเป็นความบังเอิญ ไม่ใช่ผลของ sentinel

**และบังคับ sentinel ผ่าน schema ไม่ได้ด้วย** ลองใช้ `Literal` แล้ว Pydantic สร้างออกมาเป็น

```json
"anyOf": [{"type": "string"}, {"const": "NOT_FOUND", "type": "string"}]
```

สาขาแรกครอบสาขาที่สองอยู่แล้ว decoder จึงไม่ได้บังคับอะไรเพิ่ม sentinel เป็นได้แค่คำสั่งใน description
ซึ่งโมเดลจะทำตามหรือไม่ก็ได้ (ผลจริงคือมันตอบ `'Not specified'` แทนที่จะเป็น `NOT_FOUND` ตามที่สั่ง)

**บทเรียนที่เขียนลงรายงานได้** นี่คือ**ผลลบที่มีค่า** เราตั้งสมมติฐาน ทดสอบ และปฏิเสธมัน
รายงานที่มีแต่สิ่งที่ได้ผลอ่อนกว่ารายงานที่แสดงว่าเคยลองอะไรแล้วไม่ได้ผลด้วย

# ส่วนที่ 4 เรื่องข้อจำกัด

## 4.1 n=3 หมายความว่าอะไรทางสถิติ

**คำตอบสั้น แทบไม่ได้อะไรเลยทางสถิติ แต่การทดลองแบบมีตัวควบคุมไม่ได้พึ่งขนาดตัวอย่าง**

อันนี้เป็นจุดที่ละเอียดและถ้าตอบได้จะดูดีมาก

**ทำไม n=3 อ่อน** ถ้าอยากบอกว่า "ระบบนี้แม่น X%" บนเอกสารทั่วไป สามใบตอบไม่ได้เลย
ช่วงความเชื่อมั่นจะกว้างจนไร้ความหมาย 3/3 อาจมาจากระบบที่แม่นจริง 95% หรือ 50% ก็ได้ แยกไม่ออก

และเอกสารทั้งสามใบ**สร้างจากสคริปต์เดียวกัน** เลย์เอาต์เหมือนกัน ไม่มีภาษี ไม่มีค่าส่ง ไม่มีหลายหน้า
ไม่มีสแกน จริง ๆ แล้วมันใกล้เคียง n=1 ที่ทำสามสำเนามากกว่า n=3

**แต่การทดลอง schema เป็นคนละประเภท** มันไม่ใช่การสำรวจตัวอย่างเพื่อประมาณค่าประชากร
มันคือการทดลองที่เปลี่ยนตัวแปรเดียวแล้วดูผล

ข้อสรุปคือ **"schema เป็นสาเหตุ"** ซึ่งได้รับการสนับสนุนจากสองอย่าง

หนึ่ง **กลไกที่อธิบายได้** เรารู้ว่า `required` list ว่างทำให้ decoder ยอมให้ข้าม ไม่ใช่แค่เห็นความสัมพันธ์

สอง **การสลับตัวแปรแล้วผลกลับทิศทันที** 3/15 เป็น 15/15 ทุกใบ ไม่ใช่ดีขึ้นบ้างบางใบ

**ประโยคที่ใช้ตอบได้** "n=3 ไม่พอจะอ้างเรื่องความแม่นยำ แต่ข้อสรุปของเราไม่ใช่เรื่องความแม่นยำ
เป็นเรื่องสาเหตุ ซึ่งพิสูจน์ด้วยกลไกและการทดลองแบบมีตัวควบคุม ไม่ใช่ด้วยขนาดตัวอย่าง"

## 4.2 ทำไม 15/15 ถึงยังไม่พอจะบอกว่าแก้ปัญหาแล้ว

**เหตุผลสี่ข้อ**

**หนึ่ง เอกสารทดสอบง่ายเกินไป** สร้างเอง เลย์เอาต์สะอาด มี text layer ครบ ไม่มีภาษี ไม่มีค่าส่ง
ไม่มีหลายหน้า ไม่มีสแกน ใบจริงยากกว่านี้ทุกมิติ

**สอง ทุก field มีอยู่จริงในทั้งสามใบ** การทดลองจึงวัดแค่ "หาเจอไหมเมื่อของมีอยู่"
ไม่ได้วัดว่า "ทำอะไรเมื่อของไม่มี" ซึ่งพอวัดแยกก็พบว่ามันแต่ง 3 ใน 9 เคส

**สาม เรายังไม่ได้แก้จริง** 15/15 มาจากคลาสทดลองในไฟล์ evaluation ไม่ใช่จากโค้ดที่รันจริง
ระบบตอนนี้ยังได้ 3/15 อยู่

**สี่ gate ยังรับไม่ไหว** พอ required บังคับให้โมเดลตอบ มันจะแต่งค่า และ gate ปัจจุบัน
ตรวจยอดเงินได้แล้วก็จริง แต่ `invoice_number` กับ `vendor_name` ยังเช็คแค่ว่า "ข้อความนี้มีในเอกสารไหม"
ซึ่ง `Table 4` ผ่านได้สบาย

**ประโยคที่ใช้ตอบได้** "15/15 พิสูจน์สาเหตุ ไม่ได้พิสูจน์ว่าระบบพร้อมใช้
และการเอาไปใช้จริงต้องแก้ validation gate ก่อน ไม่งั้นเราแค่เปลี่ยนความล้มเหลวที่มองเห็นได้
เป็นความล้มเหลวที่มองไม่เห็น"

# ส่วนที่ 5 คำถามที่ยากที่สุด

## 5.1 ถ้ารู้ว่าแก้ยังไงแล้ว ทำไมยังไม่แก้

**นี่คือคำถามที่ต้องเตรียมคำตอบมากที่สุด** เพราะถ้าตอบไม่ดีจะฟังเหมือนข้อแก้ตัว

**มีเหตุผลสามข้อ เรียงจากแข็งไปอ่อน**

### เหตุผลที่ 1 แข็งที่สุด gate ยังรับไม่ไหว

การแก้ schema ทำให้โมเดลแต่งข้อมูลราว 33% ของ field ที่ไม่มีจริง และ gate ปัจจุบันจับไม่ได้ทุกกรณี

```
ยอดเงิน         gate ตรวจได้แล้ว ต้องอยู่ใกล้คำว่า Total
invoice_number  ยังเช็คแค่ substring  ->  'Table 4' ผ่าน
vendor_name     ยังเช็คแค่ substring
```

**ถ้าแก้ schema ตอนนี้ เราจะเปลี่ยนความล้มเหลวที่เห็นได้ (ช่องว่าง) เป็นความล้มเหลวที่เห็นไม่ได้
(ค่าที่แต่งขึ้นและติดป้ายว่าผ่านการตรวจแล้ว)** ซึ่งแย่กว่าในระบบที่เกี่ยวกับเงิน

อันนี้เป็นเหตุผลทางวิศวกรรมล้วน ๆ และเกิดจากการวัด ไม่ใช่ข้อแก้ตัว

### เหตุผลที่ 2 กฎการแบ่งงานในทีม

`ExtractedInvoice` และ `DocumentExtractor` เป็น lane ของ JJ และกฎในโปรเจกต์ระบุว่า
การแก้ไฟล์คนอื่นต้องไปทาง pull request พร้อมหลักฐาน ไม่ใช่ commit ตรง

**และเรายกกฎนี้ไปเตือนคนอื่นด้วย** ถ้าข้ามเอง กฎก็ใช้ไม่ได้อีกต่อไป

หลักฐานว่าจริงจัง PR #1 ที่เปิดไว้ไม่ได้แตะไฟล์ของ JJ กับ Luke เลยสักบรรทัด

### เหตุผลที่ 3 อ่อนที่สุด รอกลุ่มตัดสินว่าจะรายงานยังไง

กลุ่มยังไม่ตกลงว่าจะรายงานผลแบบไหน แต่**ข้อนี้อ่อนเพราะไม่ได้บล็อกจริง**
ตัวเลข 3/15 ถูกแช่ไว้ในไฟล์ `evaluation/results_before.json` ตั้งแต่ 26 ส.ค. แล้ว การแก้ทำลายมันไม่ได้

**ถ้าโดนถามซ้ำให้ยอมรับข้อนี้** ว่าเคยใช้เป็นเหตุผลแต่ตรวจแล้วมันไม่ใช่เหตุผลจริง เหลือสองข้อแรกที่ยืนได้

### สิ่งที่ทำแทนการแก้

ไม่ได้นั่งรอเฉย ๆ

```
วัดสาเหตุจนพิสูจน์ได้          schema_comparison.py
วัดต้นทุนของทางแก้            sentinel_comparison.py
ปฏิเสธทางแก้ที่ใช้ไม่ได้        sentinel
แก้ gate ให้ตรวจยอดเงินได้      validation-gate-spec.md
เพิ่ม reconciliation           จับเคสที่โมเดลคำนวณเลขขึ้นมาเอง
เตรียม PR พร้อมหลักฐาน         รอ JJ บอกว่าพร้อม
```

**ประโยคที่ใช้ตอบได้** "เรารู้วิธีแก้และวัดผลไว้แล้ว แต่การแก้จะทำให้โมเดลแต่งข้อมูลในกรณีที่ field
ไม่มีจริง ซึ่งเราวัดได้ว่าเกิดราวหนึ่งในสามของกรณี ประตูตรวจสอบของเรายังจับได้ไม่ครบทุกช่อง
เราจึงเลือกทำประตูให้แข็งก่อน และเก็บการแก้ไว้ให้เจ้าของโค้ดในทีมเป็นคนตัดสินใจ"
